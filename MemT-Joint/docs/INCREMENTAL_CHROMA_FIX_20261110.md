# Chroma 重复复制与编码性能修复

## 原因与修改

旧实现的事务克隆会深拷贝完整状态，再创建全套物理集合、重新嵌入并写入历史文档。
Mem-T 更新工具采用增量 add/upsert；本次保留该检索和写入语义，消除分支管理导致的重复工作。

- State.clone 复制独立的字典映射，复用不会就地修改的历史文档、metadata 和版本记录。写入始终替换条目；对外快照仍深拷贝。
- 逻辑分支不直接写入 Chroma；同步搜索前将目标分支与当前物理视图比较，只 upsert 差异、delete 不可见条目。
- 每个 runtime 按文本缓存原始 Chroma BGE 嵌入函数输出；文档及 query 都通过原始函数编码，不改变归一化设置、向量距离和 top-k 参数。
- 同一 runtime 顺序执行搜索。切换到历史分支时删除未来条目；该共享可变视图不适用于未经同步的并发搜索。
- 会话结束时保存历史快照，避免同一会话每个块反复覆盖快照。问题的 eval_session 仍对应完整会话结束状态。
- 逐块记录 generation_seconds、Chroma 编码/同步耗时、新编码文本数、增删行数。sync_seconds 包含其内部的编码时间，不能与 embedding_seconds 相加。
- 复用已完成的 step50 actor 导出；每次评测仍用新 run 从空状态建库，不复用记忆或旧分数。

## 验收

远程私有 memt-joint 环境中 31 项回归通过（52.61 秒）。真实 Chroma 连续 40 次分支切换只编码 2 段不同文本；客户端保持 1 个，物理集合保持 1 个，线程 54→55，历史分支无未来条目。

实际 BGE-M3 CPU、Chroma 1.0.9，同样的 16 条初始文档和 3 次克隆/更新/搜索：

| 测量项 | 修复前 | 修复后 |
|---|---:|---:|
| 重复操作耗时 | 10.8294 s | 1.0361 s |
| 测量阶段编码文本数 | 54 | 3 |

该操作加速 10.45 倍；真实 BGE 检索 IDs、顺序及 metadata 与新建普通 Chroma 库一致。
两组均先建立并预热各自索引；模型首次加载时间没有纳入上述测量，不能用两组 warmup 时间比较加速。
这不是完整 Qwen 建库或 81 题评测的加速比。
